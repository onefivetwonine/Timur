# Talent V0.1 engineering milestones

{% hint style="info" %}
**Shared tracker for GitHub and GitBook.** These six milestones turn the repository foundation into a **provable Talent decision loop**. They do not approve live personal data, fused match scores, autonomous outreach, Opportunity H0.3, or microservices.
{% endhint %}

Engineering companion to the product [Delivery roadmap](https://app.gitbook.com/s/FkviPqGRiQmXp5lCD9IA/product-strategy/delivery-roadmap) and the repo [implementation roadmap](implementation-roadmap.md). Update status here when a milestone’s exit evidence is recorded.

## What “done” means overall

When all six milestones pass, Timur can honestly claim:

> For one frozen Singapore role family, on **synthetic** data, the system retrieves people, assesses evidence under versioned gates, **blocks** actions without authority, records an auditable Decision Envelope, and measures shortlist quality against adjudicated truth — without relying on an opaque AI score.

Until then: foundation and adapters exist; **Talent decision intelligence is not yet demonstrated**.

## M1 — Claims in the database

**Build:** Idempotent, tenant-scoped loader from manual quarantine and provider snapshots into PostgreSQL (`employers`, `subjects`, `source_artefacts`, `evidence_claims`, `subject_external_ids`). Validate shapes with `@timur/contracts` where applicable. No outreach; contact fields stay behind authority.

**Exit evidence**

- [ ] Loader job (or scripted path) writes claims under RLS with provenance (`provider`, artefact hash, observed time, verification state)
- [ ] Re-running the same snapshot does not duplicate canonical claims
- [ ] Cross-tenant read/write denied in automated tests
- [ ] Documented how to load one synthetic fixture end-to-end

**When we have this, it means**

Timur has a **real evidence graph**, not only ignored local snapshots. Retrieval and gates can query facts. Enrichment vendors are inputs to claims — not decision authority.

---

## M2 — End-to-end synthetic Talent loop

**Build:** Cohesive modules for intake → parse/claim emission → identity review hooks → retrieval → gates → Decision Envelope → audit/outbox consumer on synthetic fixtures. Deterministic provider only; external AI remains off.

**Exit evidence**

- [ ] One synthetic Opportunity Twin completes the loop and writes a Decision Envelope
- [ ] Envelope includes evidence assessments, gates, `next_action`, and policy/schema versions
- [ ] Worker (or equivalent) claims outbox work idempotently; poison work is bounded
- [ ] `npm run check` (and relevant loop tests) pass on the recorded path

**When we have this, it means**

Timur is a **working decision procedure**, not a scaffold. The product question — who to review next, on what evidence, with what unknowns — has an executable answer path.

---

## M3 — Authority as a hard product gate

**Build:** Purpose- and action-scoped `AuthorityGrant` checks on processing and suggested actions. Missing, expired, or wrong-purpose grants must block. Make the failure path a first-class demo, not an afterthought.

**Exit evidence**

- [ ] Automated test: valid loop with grant → permitted suggested action
- [ ] Automated test: same loop without grant (or wrong purpose) → `blocked` / no side effect
- [ ] No code path can mark outreach/contact as executable without a grant check
- [ ] Short demo script or fixture documented for stakeholders

**When we have this, it means**

Timur is **governed decision support**. Compliance and agency buyers can see that policy is enforced in software, not promised in a slide. This is the clearest contrast with “just draft an AI.”

---

## M4 — Frozen role family + Precision@K

**Build:** Product owner freezes one Singapore role family, labeling rubric, golden-set provenance, and numeric thresholds. Run offline evaluation (e.g. Precision@10 / Best-5 agreement) against adjudicated labels. No quality marketing claim before this.

**Exit evidence**

- [ ] Written freeze record (role family, rubric, fixture IDs, thresholds) under `tests/evaluation/` or linked ops evidence
- [ ] Reproducible evaluation command on synthetic/golden fixtures
- [ ] Baseline and holdout results recorded; unknowns/failures not silently scored as hits
- [ ] Explicit statement: results do **not** authorize live personal data

**When we have this, it means**

We can measure whether the **decision procedure** surfaces the right people — not whether a model sounds confident. Ranking quality becomes evidence, not aspiration.

---

## M5 — Explainability surface

**Build:** Recruiter-facing (or API-readable) **why-this / why-not** views driven by the Decision Envelope: claim refs, gate failures, contradiction/staleness signals that force `unknown` or weaken assessments. Prefer inspectability over a single score.

**Exit evidence**

- [ ] For a recommended subject, UI or API returns dimension assessments with resolvable claim refs
- [ ] For a rejected/excluded subject, failed gates and missing evidence are visible
- [ ] At least one contradiction or stale-claim fixture produces an explicit unknown/weak outcome
- [ ] No fused match percentage introduced as product truth

**When we have this, it means**

Recruiters can **defend** a shortlist. Timur’s intelligence is visible as evidence and rules, which is what agencies need in contested or regulated hiring conversations.

---

## M6 — Pilot trust controls

**Build:** Minimum controls before any controlled-data conversation: independent deletion/revocation ledger design+implementation path, restore replay that cannot resurrect withdrawn permissions, and Singapore-credible employer join (UEN / ACRA or equivalent) on Opportunity Twin employers. First-party agency history remains the highest-trust claim path when authorized — stub the intake contract even if full integration waits.

**Exit evidence**

- [ ] Deletion/revocation ledger exists outside the DB blast radius (or verified equivalent) with replay procedure
- [ ] Restore drill notes include deletion replay and authority withdrawal checks
- [ ] Employer records can attach Singapore UEN (or documented deferred blocker with owner)
- [ ] First-party history intake contract documented (even if connector deferred)

**When we have this, it means**

Timur is **safe to discuss** as a controlled-data pilot candidate. Trust machinery is no longer “runbook fiction only.” Live data still requires a separate named acceptance — this milestone does not grant it.

---

## Explicitly out of these milestones

| Out of scope | Why |
| --- | --- |
| Fused match % / autonomous reject or outreach | Product redlines |
| External AI as decision path | Foundation lock; deterministic only until deliberate acceptance |
| Opportunity H0.3 as a second V0.1 API | Uncommitted hypothesis |
| Microservices for empty domains | Modular monolith + worker until a measured trigger |
| Live personal data in POC | Requires controlled-data acceptance after M1–M6 trust bar |
